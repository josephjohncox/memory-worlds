# Guided local and hybrid setup

## Outcome

Provide one script, one declarative configuration and one interactive flow for
running a local authority or a local authority connected to an existing corporate
service. Reuse the current service, scope, router, Graphiti and OAuth contracts.
The setup controller provisions local resources and client configuration; it does
not become a second memory server or a corporate identity administrator.

Use a Python controller exposed through `memory-worlds setup`, with thin mise and
shell entrypoints. Python already supplies TOML parsing and the project supplies
typed validation, authentication and provisioning. A shell-only installer would
duplicate secret and recovery logic. A full TUI or deployment manager adds a
second interface before the basic workflow is reliable.

## User flow

`scripts/setup.sh` and `mise run setup` launch the same terminal wizard. The
script checks prerequisites and uses the locked mise tools/dependencies; it does
not install system packages or silently trust source. The installed Python CLI
supports the same setup flow without requiring a source checkout.

The wizard collects, in order:

1. Local only or local plus corporate, and an installation name.
2. A new local authority or explicit adoption of an existing local authority.
3. Owner, private paths and loopback API/graph ports.
4. Explicit Graphiti extraction and embedding providers, models, endpoints,
   embedding dimensions and secret-file references. No paid model is chosen
   automatically and graph processing is not silently disabled.
5. For hybrid use, the trusted corporate URL and an existing user token or the
   issuer/public native client/scopes for device login.
6. Corporate shared worlds selected from authenticated user discovery. Show
   names, kinds, aliases and canonical IDs; preselect none. Exclude private worlds.
7. Desired generated Pi profiles and an optional MCP configuration example.
8. A redacted review of paths, endpoints, provider destinations, authorities,
   selected worlds, credential audiences and file changes before applying.

The wizard saves a configuration that can be reviewed, edited and applied through
the same noninteractive commands. Missing required values fail in scripted mode;
they never unexpectedly trigger prompts. Interactive secret input is hidden and
saved only in private referenced files, not the declarative config or stdout.

## Scriptable commands

| Command | Contract |
| --- | --- |
| `setup` / `setup init` | Interactive configuration and review; explicit apply uses the same apply path |
| `setup validate --config FILE` | Offline schema/path/reference validation; no writes or network |
| `setup plan --config FILE` | Describe planned changes without creating resources or reading source content |
| `setup connect --config FILE` | Explicit normal-user corporate login/discovery; no source/publication or administrative writes |
| `setup apply --config FILE` | Provision or resume owned local resources and generated files |
| `setup run --config FILE` | Start the owned graph and run the configured daemon in the foreground |
| `setup doctor --config FILE` | Read-only diagnostics, with explicit configuration/online check results |
| `setup down --config FILE` | After the daemon stops, stop only owned graph resources while retaining data |

Configuration-driven apply requires no interactive answers. Device login remains
an explicit human authorization flow; unattended setup can supply an existing API
token file. Setup does not promise unattended OAuth refresh.

## Configuration and files

Use one strict TOML schema, parsed as data rather than sourced as shell. It
selects local/hybrid mode, installation identity, local owner/data/state paths,
loopback ports, provider/model settings, secret-file references, optional
corporate connection and canonical shared-world allowlist, and client outputs.
Relative paths resolve against the configuration file; home paths are expanded
explicitly. Reject unknown fields and credential-bearing URL values.

Default locations separate configuration, private operation state and durable
data beneath the user's config/state/data directories. Private directories are
0700 and secret files 0600. Graph credentials and one-time local operator/agent
credentials are generated by the controller. Provider keys and corporate tokens
use referenced private files. The config and redacted receipts contain no secret
values, source documents or transcripts.

Generated outputs include the runtime settings, a graph-only Compose definition,
the router mount file, private credentials, setup receipt and selected Pi/MCP
profiles. Installed-package setup must carry the needed runtime template rather
than assume `deploy/` exists beside the CLI. Use a stable setup-owned Compose
project/volume identity to avoid modifying another installation's graph.

Do not overwrite global Pi configuration, shell profiles, existing unrelated
files, Kubernetes resources or unowned authority directories. Offer explicit
profile launch commands. Adding OS login services or changing global defaults is
a separate operation, not an installation side effect.

## Authority ownership, repeatability and interrupted setup

Serialize setup operations with a dedicated lock. Provision a local SQLite
authority only while its daemon is stopped, under the existing ownership lock.
An existing data directory without matching setup ownership requires explicit
adoption and a valid existing local administrator credential. Corporate login
never supplies local administration. Refuse reset/reinitialization shortcuts.

Planning and doctor must not construct MemoryStore merely to inspect a path:
its constructor initializes storage. They must leave absent/existing authority
directories unchanged. Online diagnostics may inspect authorized metadata,
identity and health, but not read source contents or write probe memories.
Ordinary OAuth authentication can create sessions/private-work identity state
and reconcile memberships from signed claims. Online doctor/connect use that
normal authentication contract; they do not promise a side-effect-free corporate
GET request or suppress its authorization reconciliation.

Persist canonical setup-owned world, scope and credential identities in authority
metadata transactionally with their creation. Names/aliases are display and
selection conveniences, not recovery keys. Store file intents, configuration
digest, authority binding and completed stages in a private operation journal.
Repeat application reuses the same resources and secret files. Report changed
grants, revoked credentials or conflicting file contents before changing access;
do not repair them by silently issuing broader credentials.

The one-time administrator/agent secret must be durably written and fsynced
before committing the corresponding new credential. An interruption must leave
matching recoverable state or an unapplied private file intent, never a committed
authority whose only administrator secret was lost. Test interrupted execution
at each provisioning boundary and concurrent repeated apply.

Owned files are written through bounded private descriptors and atomic rename.
Reject links/special files, unexpected replacement and unrelated existing files.
Only explicitly owned outputs can be replaced; preserve the user's other data.

## Local runtime

The first runtime uses the host Python daemon and an authenticated loopback
FalkorDB container with persistent owned volumes. Provider settings come from
the validated config and private references, not accidental corporate database
environment variables. Graphiti remains the default extraction/recall engine.

Apply provisions configuration and local resources without starting background
daemons or calling a model. Run starts the graph, waits for bounded health checks
and serves the owning API in the foreground; it does not initialize an authority.
An occupied port, running owner or authority/config mismatch fails visibly.
Stopping setup-owned containers retains volumes. No automatic `down -v`, data
removal, systemd/launchd registration or corporate infrastructure provisioning.
Ctrl-C stops the foreground daemon and retains the running graph. Down refuses
while that daemon owns its data-directory lock; after it stops, down removes only
the setup-owned graph containers/network and retains the persistent volumes.

## Hybrid and generated client defaults

Reuse device login and authenticated `me`/discovery with an ordinary corporate
API access token. Pin corporate authority and user identities in setup state.
Discovery cannot authorize a private world as a router mount or broaden the
selected shared-world allowlist. The corporate service and its OIDC/group mapping
are operator prerequisites; existing Helm guidance remains the deployment path.

Generate a separate local work credential and private work world/scopes alongside
the personal credential/world/scopes. The corporate mount grants only the local
work credential ID a reader role, with `publish: false` and no default user-wide
grant. Private corporate work remains a direct corporate connection.

Generated personal profiles use personal credentials and no corporate mounts.
Hybrid research profiles use the local work credential and selected mounts, with
no default writeScope, automatic capture off and automatic retrieval off. Direct
corporate profiles use the corporate endpoint/token without local scope IDs or
mounts. Generated profiles do not enable sharing, publication or global capture.

Explicit reconnect validates a new private token against the pinned corporate
authority and user before replacing the managed token atomically. Preserve the
world allowlist and report removed access. Token replacement needs no daemon
restart; a changed mount list does. Fresh corporate private-scope grants, blocked
outbox retries and local-agent rotation remain explicit authorized actions.

## Verification and limits

Test the same flow interactively and noninteractively, pure local and hybrid.
Verify exact repeat identity, interrupted bootstrap/apply recovery, exclusive
ownership, authenticated adoption, preservation of unrelated files and refusal
of drift or unsafe paths. Assert no secrets in logs, receipts, generated client
configuration or artifacts. Confirm generated Pi settings through the current
native parser and corporate mount authorization through the current API.

Exercise local startup/health/shutdown against the owned graph with local model
emulators, plus existing local OIDC emulation for hybrid user discovery where
needed. No live Okta tenant or paid model call is required. Doctor distinguishes
configuration, daemon and backend readiness from successful model extraction.
Use the checked-in mise checks and artifact audit; do not add alternate toolchains
or compatibility readers for earlier setup formats.
